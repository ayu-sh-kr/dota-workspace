# Plugin Artifact Generation

Take the sorted metadata from `plugin-source-scanning` and produce output. Keep
these functions **pure of the Vite lifecycle** — they accept metadata and return
strings (or write files), so they can be unit-tested directly. The lifecycle
skill (`plugin-build-watcher`) decides *when* they run. The metadata may describe
components, routes, an event map, or anything else — nothing here is
component-specific.

## Choose the output mechanism first

Three ways to get output to consumers; pick by what the consumer needs:

| Mechanism | Use when | How |
| --- | --- | --- |
| **Virtual module** | Runtime code imports the generated result (`import x from 'virtual:...'`) | `resolveId`/`load` return generated *source text*; nothing hits disk (Mode A) |
| **`this.emitFile`** | The artifact belongs in the **build output/bundle** | emit from a build hook so Rollup places and hashes it; participates in the graph |
| **`writeFile`** | The artifact is a **project-level file** consumed by tooling, not the bundle (Web Types JSON, CEM, `.d.ts`) | write to the package dir and register it (Mode B) |

Prefer a virtual module when the value is imported at runtime — it needs no disk
I/O and invalidates cleanly. Prefer `this.emitFile` for anything that should ship
inside the build. Use `writeFile` only for side-channel files that other tools
(IDEs, `package.json` discovery fields) read directly. Do not `writeFile` into
the bundle output dir to fake an emit.

## Mode A — virtual-module source codegen

The plugin generates ES-module *source text* that Vite serves for a virtual
import. Nothing is written to disk. Reference:
`packages/plugins/dota-vite-preloader/src/domain/*.domain.ts`.

Build the module as a string of imports + an export:

```ts
function normalizeRelativeImportPath(filePath: string): string {
  return filePath.startsWith("./") ? filePath : `./${filePath}`;
}

export async function resolveComponentExport(candidates: DotaComponentCandidate[]): Promise<string> {
  const imports = candidates
    .map(c => `import { ${c.name} } from '${normalizeRelativeImportPath(c.filePath)}';`)
    .join("\n");
  const exports = `export default [${candidates.map(c => c.name).join(", ")}]`;
  return `${imports}\n\n${exports}`;
}
```

Rules:

- Import paths must be relative and forced to start with `./` — a bare
  `src/x.ts` is treated as a bare-module specifier by Vite.
- Emit in candidate order (already deterministic from the scan) so the served
  module is stable across requests.
- For richer output (route config objects, an event→payload map), assemble each
  entry from an array of `key: value` strings and `join(", ")`; append optional
  fields only when present. See `prepareRouteConfigExport`.
- To embed a user expression verbatim (a route `render` factory), reuse the
  source printed by the scanner (`printExpressionSource`), never re-serialize a
  parsed value.

### Codegen string-safety

You are emitting source text, so treat scanned values as untrusted:

- **Never string-concatenate a scanned *value* into a code position.** Emit data
  values through `JSON.stringify(value)` (valid JS literal, escapes quotes and
  newlines), not `'${value}'`.
- **Identifiers** interpolated as bindings (a class name, an imported symbol)
  must be validated as identifiers upstream in the scan; do not accept arbitrary
  strings into an `import { X }` position.
- **Emit a leading source comment** (e.g. `// generated by vite-plugin-<slug> — do not edit`)
  so the served module is self-identifying in devtools.
- If a generated module is large or maps back to real source, return
  `{ code, map }` from `load` with a sourcemap rather than a bare string.

The public/resolved virtual IDs and the `resolveId`/`load` wiring that returns
these strings live in `plugin-build-watcher`.

## Mode B — written/emitted JSON artifacts

The plugin writes JSON files to the package and registers them in
`package.json`. Reference: `packages/plugins/web-type-json/src/main.ts`
(`createWebTypesSchema`, `createCustomElementsManifest`,
`writeGeneratedArtifacts`).

### Build the schema object (pure)

Keep each serializer a pure function `metadata → schema object`, typed by a named
contract in `Types.ts` (`WebTypesSchema`, `CustomElementsManifestSchema`). When
one scan feeds multiple formats, project the *same* metadata into each — never
rescan per format. Re-sort inside the serializer if that format needs a
different stable order (CEM sorts modules by path, declarations by class name).

### Write coordinated, deterministically

```ts
const json = JSON.stringify(createWebTypesSchema(infos), null, 2);   // 2-space indent
await writeFile(resolve(root, outFile), json, "utf-8");
```

- Always `JSON.stringify(obj, null, 2)`. Determinism comes from sorting the
  metadata, not from stringify.
- Writing several artifacts: build all strings first, then `Promise.all` the
  writes. Guard that two artifacts never resolve to the **same** output path
  (throw early if two formats collide).
- Enforce ownership and path safety before emitting a module path:
  `CustomElementsManifestUtils.isPackageOwnedSource` excludes external scan
  roots; `normalizeModulePath` rejects empty, absolute, or `..`-escaping paths;
  `defaultModulePath` swaps `.ts` → `.js` and normalizes slashes. A manifest may
  only advertise files inside its own package.

### Register in package.json — one read-modify-write

After writing artifacts, update `package.json` **once**, preserving unrelated
fields, and only write it back if something changed:

```ts
const pkgPath = resolve(root, "package.json");
const pkg = JSON.parse(await readFile(pkgPath, "utf-8")) as PackageJsonWithGeneratedArtifacts;
let changed = false;

const webTypesEntry = `./${outFile.replace(/^\.\//, "")}`;
if (pkg["web-types"] !== webTypesEntry) { pkg["web-types"] = webTypesEntry; changed = true; }
// ...customElements entry when CEM is enabled and updatePackageJson is set

if (changed) await writeFile(pkgPath, `${JSON.stringify(pkg, null, 2)}\n`, "utf-8");
```

- Do the read-modify-write in a single coordinator so concurrent writers cannot
  clobber each other's discovery fields.
- Preserve a **trailing newline** on `package.json` to avoid churn in diffs.
- Type the parsed package with an open contract
  (`PackageJsonWithGeneratedArtifacts`, `[key: string]: unknown`) so untouched
  fields survive.

## Configuration normalization

Opt-in output (like CEM) should be normalized once, before build or watcher runs,
so lifecycle code never re-handles shorthand. `true` → defaults; `false`/absent →
disabled; object → validated fields. See
`CustomElementsManifestUtils.normalizeConfig`. Store the result as a
`Normalized…Config` named type.

## Best practices

- **Serializers are pure and total** — same metadata in, byte-identical output
  out, no lifecycle, no clock, no globals.
- **One scan, many projections** — feed every format from the one metadata array.
- **Decide the mechanism deliberately** (virtual / emitFile / writeFile) rather
  than defaulting to disk.
- **Escape data, validate identifiers** in any codegen path.
- **Self-identify generated files** with a header comment or a `generatedBy`
  field so they are never mistaken for hand-authored source.

## Review checklist

- Is the output mechanism (virtual module / `emitFile` / `writeFile`) the right
  one for how the artifact is consumed?
- Are serializers pure functions returning named-typed schema objects?
- Is output deterministic (sorted upstream, `null, 2` indent)?
- For virtual modules: are import paths relative and `./`-prefixed, data values
  emitted via `JSON.stringify`, and identifiers validated upstream?
- For JSON: are all strings built before any write, with `Promise.all`, and a
  same-path collision rejected?
- Are module paths ownership-checked and escape-rejected before publication?
- Is `package.json` a single guarded read-modify-write that keeps a trailing
  newline and preserves unrelated fields?
- Is opt-in configuration normalized once into a named type?
